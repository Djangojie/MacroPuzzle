# 交互与拼图规则 v0.1

## 1. 主流程

`今日拼图 → 拍照/选图（可跳过）→ 选演示食物或手动输入 → 确认份量和来源 → 保存 → 拼图更新 → 查看推荐 → 带入表单并再次确认`

四个主页面：今日、记录、推荐、设置。今日页可选日期、看列表、编辑与删除。记录页显示图片只作记忆辅助，选择图片后不触发营养结论，也不上传图片。推荐页给原因与不确定性。设置页解释目标来源，并提供本机 API 数据清除。数值到 SVG 的完整映射见 `09-PUZZLE-ENGINE.md`。

## 2. 拼图语义

- 正方形只是视觉容器，分为蛋白质 P、碳水 C、脂肪 F 三个固定区域；首版沿用原型的 30%/45%/25% 高度作为**视觉权重**，不是科学推荐比例。
- 每个区域填充率 `min(当前克数 / 用户目标克数, 1)`；目标必须为正数。超出量另以 `+X g` 和文字提示展示，不能靠颜色表达。
- 三个目标均有效时，综合“已填充” = 三个区域填充率算术平均，四舍五入为整数；否则显示“进度待设置”。这只表示相对于用户输入目标的进度，不是健康分数。
- 能量另设进度条；不纳入拼图平均，以免同一营养素重复计权。能量显示依据数据源提供的热量；可对比 4/4/9 估算值但不静默覆盖包装值。
- 空记录时为 0；任意目标缺失时显示“目标未设置”，不除零。超出目标时仍显示真实摄入与超出量。
- 时间按用户本地日期归档（`YYYY-MM-DD`）；改变时区后保留原记录日期，不暗中迁移。

## 3. 记录细节

- 字段：食物名、份量数值+单位、P/C/F 克数、能量 kcal、来源类型（演示/包装/数据库/手填）、记录日期；可选照片预览。
- 单位不能只用“倍数”而没有基准：演示食物须显示“每 100g”“每个”等基准。录入单位可用 g、份；每份的克重未知时不推算。
- 所有数字有限且非负；份量必须大于 0；数值上限只做输入防错，遇到极端值给确认，不自动判定饮食问题。
- 切换预设后，清楚标出数值是演示值；手改任一字段后来源变为“手动修正”。
- 删除支持确认与短时撤销，避免误触。历史日期可直接查看和编辑。

## 4. 推荐规则（首版启发式，待用户验证）

1. 只用用户确认后的当日 P/C/F、能量和有来源的候选食物；首版候选是演示数据。
2. 对每个候选计算：`benefit = Σ min(候选宏量, max(目标−当前,0))/目标`；`overflow = Σ max(当前+候选−目标,0)/目标 + max(当前能量+候选能量−能量目标,0)/能量目标`；`score = benefit − 1.3×overflow`。这是沿用原型的可解释排序，不是营养学最优算法。
3. 目标缺失、候选数据缺失/过期或用户限制无法核查时，不做个体化排序；展示普通候选与原因不充分提示。
4. 用户过敏、忌口、宗教和口味筛选在正式推荐前必须支持；首版没有这些资料，不能核查安全时只能标“演示排序”或普通候选，不能说“适合你”。
5. 同分时按候选 ID 升序保证稳定；没有正收益或条件不足时可不推荐。评分只用于演示排列，不展示为健康分数。
6. 每条展示“补充 X g P / 可能超过 Y g F”等具体理由；已满或全候选分数差时可显示“暂无明确推荐”。

## 5. 原型与新版差异

现有 HTML 有四页和六种演示食物。它的 `localStorage` 在日期变化时清空旧食物；只存当天；照片只在内存预览；无法编辑；演示数值没有逐项来源。其“适合你下一餐”等文案不符合 M1 的演示排序边界。新实现应修复这些差距，保留轻松、非评判的文字方向。
