# 2026 年 AI 辅助开发建议流程

以下是针对 MacroPuzzle 的**建议工作法**，不是行业统一标准，也不声称所有团队都采用同一工具。规格驱动（spec-driven）是已有实践与工具路线；实施仍须按项目风险和反馈调整。参考 [GitHub Spec Kit 介绍](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)、[GitHub AI 代码复核指南](https://docs.github.com/en/copilot/tutorials/review-ai-generated-code) 和 [OpenAI Codex AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

## 一轮 3–5 天的建议节奏

1. **从用户任务写规格**：一个可观察结果、一条非目标、真实边界、数据样例和验收步骤。文档是活的；用户反馈可改它。
2. **拆成短任务**：例如“存一餐并跨日可查”，每项能独立运行、审查和回退。不要一次交给 AI 做照片识别、账号、推荐和部署。
3. **让 Codex 实现**：给它固定输入（PRD、规则、验收）、允许修改范围和验证命令。重大改动先写执行计划。`AGENTS.md` 约束持续生效。
4. **验证代码和体验**：自动化跑计算/表单/构建；开发者看 diff、依赖和安全；用真实浏览器走用户任务。对营养内容再做专业复核。
5. **请用户试做**：观察 5 名目标用户完成记录和解释推荐；问哪里卡住、哪里不信。保存观察证据和原话，不把设计推测写成用户结论。
6. **更新规格再迭代**：将发现分为 bug、交互误解、营养疑问、范围变化；决定下一轮一个最小改动，修订文档和验收条件。

## 推荐的工作产物

每张任务卡包含：用户问题、范围/非范围、样例输入输出、边界、验收、负责人、验证记录。每次变更留一段“事实/假设/待验证”，在 `docs/08-SOURCE-AND-DECISIONS.md` 记决策和理由。复杂任务可用执行计划；OpenAI 有此类做法的[示例](https://developers.openai.com/cookbook/articles/codex_exec_plans)，其页面也提示该示例已归档，不能当成当前强制规则。

## 人与 AI 的分工

- 人负责目标用户、隐私与营养风险、取舍、试用观察、发布决定。
- Codex 负责在给定约束内读代码、实现小块功能、测试、解释差异和更新文档。
- AI 产出的依赖、API、测试和文案都要核查。GitHub 官方指南建议检查编译/测试、意图匹配、依赖来源与 AI 特有错误；这支持“人审 + 自动检查”的组合，不能解释为 AI 代码天然可靠。

## 产品与软件磨合的具体闭环

`设计假设 → 可点击原型 → 小范围任务观察 → 记录证据 → 修正规则/文案 → 小步开发 → 自动与人工验收 → 下一轮观察`。当前 HTML 已覆盖“可点击原型”；它不是实测反馈。下一轮优先观察：用户能否理解三色不是健康评分、是否会确认份量、是否信任推荐解释。
