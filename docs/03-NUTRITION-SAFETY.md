# 营养计算、来源与安全边界 v0.1

## 1. 计算规则

- 存储原始录入值与标准化后的克数/能量，不用显示时四舍五入后的值再计算。显示：宏量 1 位小数、能量整数；合计最后再舍入。
- 数据按“每基准份 × 用户份量”缩放；基准份与单位必须存档。例如“每 100g，食用 150g”，系数 1.5。
- `P_total = ΣP_i`、`C_total = ΣC_i`、`F_total = ΣF_i`。只有该日所有记录的热量均已知时，`kcal_total = Σkcal_i`；否则为 `null` 并显示“有记录的热量未知”，不能把缺失当 0。范围判断先用原值；比例只在目标 > 0 时计算。
- 宏量估算能量 `4P + 4C + 9F` kcal 只用于提示或数据质量检查，不自动替换标签或来源热量。酒精、纤维、糖醇、四舍五入和特定食物换算可造成差异。[FDA 营养标签指南](https://www.fda.gov/media/81606/download) 给出 4/4/9 的常用近似值。
- 包装热量与宏量估算明显不一致时，标记“请核对标签/份量”，不擅自修正；阈值是产品 QA 参数，首轮可取 `max(50 kcal, 20%)` 做提示，须在真实数据中再校准。
- 同名食物不同品牌、做法、重量不能合并为一条“真值”。每条记录保留来源、来源 ID/链接、采集日期和是否用户修正。

## 2. 数据可信度

| 层级 | 示例 | UI 处理 |
| --- | --- | --- |
| 用户确认的包装标签 | 品牌、规格、日期明确 | 显示“按包装标签”，仍可能有舍入和变动 |
| 有版本的营养数据库 | USDA FDC 的明确 `fdcId` | 显示来源与版本；注意国家食物差异 |
| 用户手填 | 自制菜、外食 | 显示“用户估算” |
| 原型演示值 | 六个预设 | 醒目标“演示，不作营养依据” |
| 仅照片推断 | 外观 | 不能直接成为已确认营养值 |

USDA FoodData Central 的食物类型、份量语义并不相同；接入时要保留数据类型、来源 ID、单位和发布信息，不可把美国食品库当作中国菜完整覆盖。[USDA FAQ](https://fdc.nal.usda.gov/faq/)、[API 指南](https://fdc.nal.usda.gov/api-guide/)。

## 3. 产品边界

- 面向一般成年人做记录与搭配启发。目标值由用户自己设或日后经专业审核的方案导入；原型的 2000 kcal / P120g / C230g / F65g 仅用于演示，彼此也不完全对应能量，不能宣传为通用处方。
- 拼图不评价健康。均衡饮食还涉及食物多样性、蔬果、纤维、钠、游离糖、脂肪种类等，三大营养素不足以给健康结论。[WHO 健康饮食](https://www.who.int/health-topics/healthy-diet)。
- “薄肌”、减脂、增肌只作为用户表述研究，不做体型保证、极低热量目标、补偿性运动建议或羞辱性提示。
- 不对未成年人、孕哺、糖尿病、肾病、进食障碍风险等情况自动给个体营养目标；这类需求应转专业人员。
- 过敏原信息缺失时不能推荐为“安全”；候选数据并非过敏原认证。
- 照片无法可靠确定份量、食材和做法，所以拍照仅辅助回忆，日后识别也须人工确认。[食物图像评估综述](https://pmc.ncbi.nlm.nih.gov/articles/PMC11607557/)。

## 4. 数据与隐私

- M1 的文字记录保存在本机 FastAPI/SQLite；照片只在浏览器本地预览，不上传、不持久化；对象 URL 在关闭或取消后释放。不要把原始照片写进日志、分析、错误报告。本机 API 未启动时不能保存记录。
- 本机 SQLite 不是安全备份，也不能跨设备同步；UI 要说明换设备或删除数据库会丢失。正式版本需要导出、保留策略与明确同意后才云同步。旧 HTML 原型的浏览器记录不自动迁移，不能静默删除。
- 预设卡片与任何截图均需标注“演示数据”。若要公开发布食物营养内容，先核对来源许可、地域适用性和营养专业审阅。

## 5. 测试数据示例

纯函数测试应覆盖：空数据、0 目标保护、份量 1.5、多个食物求和、超额、缺失能量、负数/NaN/Infinity、跨日归档、来源被手改后降级、能量差异提示。预设值只用于流程测试，不用于营养准确性测试。
